# Unit 4.1 Release Design

## Decision

Release `axis-load-cases@0.1.0` after accepting ID39 and ID42 as the
historical horizontal/vertical evidence required by Unit 4.1. Their source
packets remain provenance-limited: neither packet contains an original
revision identifier, confirmed as-built installation record, or complete
correction history. The release records those limitations and does not call
the packets release-grade vendor validation.

The missing third long-stroke/high-speed historical project is not a Unit 4.1
release blocker. It remains deferred evidence for the broader Unit 0.1,
Phase 1B, and end-to-end MVP validation goals. It will be added when a real
project exists; it will not be fabricated or replaced by a synthetic fixture.

`axis-load-cases@0.1.0` remains limited to `normal` and `peak` cases.
`holding` and `emergency_stop` remain deferred until source-backed real-project
evidence exists for their semantics.

## Evidence Disposition

- Promote the ID39 and ID42 fixture metadata from `draft` to
  `release_candidate`. This means the founder accepts them for Unit 4.1's
  historical regression gate while their missing provenance remains visible.
  Set each fixture revision to `0.1.0-release-candidate`; do not label either
  fixture `release_grade`.
- Keep every source phase `unclassified`; acceleration, constant-speed, and
  deceleration phases are not silently renamed `normal`, `peak`, or
  `emergency_stop`.
- Preserve the known ID42 discrepancies, including its printed arithmetic
  typo and conflicting component/manufacturer claims, as validation
  deviations rather than correcting the historical source.
- Add an automated fixture-integrity test that recomputes SHA-256 for all
  eight ID39/ID42 source images and compares it with the fixture records.
- Use the three published THK examples as the roadmap's three published
  reference examples. Use the independently implemented Atlanta horizontal
  and vertical worked examples as the solo-review substitute.
- Register the Atlanta document as metadata-only, conservatively classified
  with `licensed` access while its redistribution status is unresolved. Its
  immutable revision records the local PDF's full SHA-256; customer-facing
  traces do not quote or link the local document.

## Module Contract Completion

The existing draft omits two inputs already promised by the Unit 4.1 and
Stage 2 contracts:

- `motion.axis.duty_cycle`
- `env.ambient_temperature`

Add both as optional, trace-only context inputs. Neither changes the rigid-body
force equations: duty cycle does not alter a per-case force, and ambient
temperature has no universal derating formula. When present, both values are
recorded in the stored calculation trace/report; when absent, the trace states
that no usage or ambient context was supplied. Tests prove that changing these
context values does not change force or moment outputs.

No parameter-registry change is required because both canonical parameters are
already released. No database, generic UI, or report-framework change is
allowed. The existing generic schemas render the added ports and stored trace.

## Immutable Source Citations

Replace the access-dated NIST webpage revision with the fixed official
publication `NIST Special Publication 811, 2008 Edition, second printing
(November 2008)`, using the official NIST PDF and Appendix B.8 for
`g_n = 9.80665 m/s^2`. Register it as a new immutable source revision and
update the manifest, trace, validation record, and source index to use that
revision. The access-dated intake revision remains unchanged for historical
records.

THK revision `515-1E` remains the primary axial-load method/reference-example
edition. Existing source metadata is not mutated.

## Validation and Release Record

Create `validation/axis-load-cases/0.1.0.md` from the project template and
complete every section:

- identity, package hash, registry version, purpose, and validity envelope;
- the fixed NIST and THK method sources with exact editions/pages;
- all three THK worked examples with inputs, computed results, tolerances, and
  pass results;
- the Atlanta independent comparison with numeric differences and scope;
- ID39/ID42 historical regressions and every known provenance/deviation note;
- unsupported `holding`, `emergency_stop`, legal/compliance claims, collision
  impact, brake sizing, structural compliance, backlash, guide-block load
  distribution, and regenerative-braking conditions;
- test-coverage checklist;
- solo-validation reviewer substitution using the Atlanta comparison; and
- sign-off and supported-use summary.

Complete the runtime `ValidationRecord` consistently: remove provisional
reviewer language, record the solo-review substitute and release date, and
preserve all limitations. Add the fixed NIST, THK, and Atlanta revision rows to
`validation/source-index.md`. ID39/ID42 remain internal fixture references,
not customer-facing source revisions.

## Test-First Release Work

Before changing the package, add focused failing tests for:

1. the two optional context ports and their trace/report presence;
2. output invariance when duty cycle or ambient temperature changes;
3. ID39/ID42 evidence status and raw-image hash integrity;
4. exact stable trace section/step IDs;
5. module input/computation serialization round trips;
6. monotonic force behavior for mass and signed acceleration in the supported
   simple cases;
7. registry discovery of `axis-load-cases@0.1.0`; and
8. conformance import-boundary and source-immutability checks running as
   `pass`, never `skipped`.

After tests drive the changes, replace the draft-only package entry point with
`index.ts`, update internal imports, generate the module registry, compute and
pin the final source-immutability hash, and confirm the sealed package content
hash in the validation record.

## Failure Handling and Release Guardrails

- Any source hash mismatch, reference-example tolerance failure, conformance
  skip/failure, registry mismatch, or documentation/runtime validation
  inconsistency blocks release.
- The module continues rejecting invalid orientation/incline combinations,
  malformed vectors, invalid mass routes, unsupported cases, and out-of-range
  friction through its existing input/schema boundaries.
- Missing optional duty-cycle or ambient-temperature context is reported, not
  silently defaulted to an invented engineering value.
- No released module or released parameter definition is edited in place;
  Unit 4.1 is still unreleased, so its `0.1.0` draft may be finalized before
  its first registry entry is created.

## Documentation and Handoff

Synchronize the Stage 1/2 records, module README, implementation map, roadmap,
source index, and progress tracker. The records must distinguish:

- Unit 4.1 complete and `axis-load-cases@0.1.0` released;
- the third real-project fixture deferred but still desired;
- `holding`/`emergency_stop` deferred to a future module version; and
- licensing/provenance limitations still open without blocking the supported
  `normal`/`peak` release.

Full release verification is: targeted tests, lint, typecheck, complete test
suite with the configured database, production build, generated-registry
cleanliness, and a final clean diff review. Once all checks pass, the tracker
advances to Unit 4.2 `motion-profile` Stage 6 release; no Unit 4.2 code is
included in this work unit.
