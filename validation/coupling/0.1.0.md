## Purpose and Supported Applications

Given a candidate flexible shaft coupling's own catalog rating data (rated
torque, maximum/shock torque, allowable rotational speed, torsional
stiffness, moment of inertia, bore diameter range, allowable misalignment)
plus the drive torque and rotational speed already resolved by `ball-screw`
(Unit 4.3), this module checks whether that specific coupling is
mechanically viable for the axis: torque capacity under steady and shock
load (with an engineer-supplied service factor), speed limit, misalignment
capability against the installation's actual offset, and bore/shaft-diameter
compatibility. It reports a required-spec / pass-fail-with-margin result for
a coupling the engineer has already identified by model — it does not
search a catalog and rank candidates
(`context/modules/coupling/stage-1-spec.md` "Purpose").

## Validity Envelope and Assumptions

- One coupling connecting a ball screw's own drive shaft to its upstream
  driving shaft — not a multi-coupling driveline.
- Only the `normal` and `peak` load cases, matching `axis-load-cases 0.1.0`'s
  and `ball-screw 0.1.0`'s own scope restriction.
- The `peak` case is checked against the coupling's own maximum (shock)
  torque, reusing `screw.drive_torque[peak]` as the required torque — a
  documented adaptation, since `axis-load-cases`' own "peak" case means a
  peak operating condition, not the motor starting-torque transient KTR's
  and R+W's own sources mean by that term
  (`context/modules/coupling/stage-2-contract.md` "Decisions" item 4).
- The shock-torque check reuses the same required-torque-times-service-
  factor shape as the steady check (closer to KTR's general framing than to
  R+W's safety-coupling-specific disengagement-multiplier form), not either
  source's own literal shock-torque formula
  (`stage-2-contract.md` "Decisions" item 3). See "Independent Method or
  Tool Comparison" below for what this simplification costs numerically.
- `coupling.service_factor` is one consolidated required input with no
  built-in default, applied identically to both cases — KTR's and R+W's own
  factor tables disagree in both category boundaries and numeric ranges, and
  neither is adopted wholesale.
- Operating rotational speed is derived locally from
  `motion.axis.case_linear_velocity` via `screw.lead`/`screw.gear_ratio`, not
  a released `screw.*` speed port. A true zero-speed case is unsupported —
  `resolveSpeedSafetyFactor` throws rather than reporting an infinite safety
  factor.
- Torsional stiffness and moment of inertia are reported outputs only, not
  evaluated pass/fail — no torsional-resonance or periodic-vibration check,
  since this project has no released motor-rotor or reflected-load-inertia
  parameter yet (Unit 4.7 territory).
- Misalignment and bore compatibility are simple bound checks against
  catalog data; no stiffness/life derating as a function of misalignment, no
  fit-tolerance (h6/h7-class) verification.

## Independent Method or Tool Comparison

**Satisfied (2026-08-10).**
`lib/modules/coupling/0.1.0/ktr-din740-benchmark.ts` implements a second,
distinct KTR document's own shock-torque method as a genuine second
computation — the roadmap's Definition of Done item 9 — and reproduces that
document's own worked example (catalog printed page 13) end to end.

- Independent method/tool: KTR Systems GmbH, "Coupling Selection According
  to DIN 740 Part II" (`us.ktr.coupling_selection_din740_part2@web-2026-08-10`)
  — found via WebSearch while looking for a published shock-torque worked
  example, since neither KTR's other document's own example nor either of
  R+W's own two examples exercises the shock-torque check with real numbers.
- Case compared: the document's own worked example — a 160 kW/1485 rpm
  rotary current motor (`J_Motor = 2.9 kgm^2`) driving a screw compressor
  (`T_LN = 930 Nm`, `J_compressor = 6.8 kgm^2`) through a ROTEX Size 90
  coupling (`T_KN = 2400 Nm`, `T_Kmax = 4800 Nm`,
  `J_KA = J_KL = 0.0673 kgm^2`).
- Result from independent method: `T_AN = 1029 Nm`; steady requirement
  `T_KN >= T_LN*S_t = 1348.5 Nm` (cleared by `T_KN = 2400`); coupled inertias
  `J_A = 2.9673 kgm^2`, `J_L = 6.8673 kgm^2`; inertia coefficient `M_A = 0.7`
  (source's own rounding); shock torque `T_S = 2593.1 Nm`; shock requirement
  `T_Kmax >= T_S*S_Z*S_t = 3760 Nm` (cleared by `T_Kmax = 4800`) — "the
  coupling is sufficiently dimensioned," per the source's own conclusion.
- MachineStudio result: `ktrDin740ExampleRequiredRatedTorqueNm()` = `1348.5`
  (exact); `ktrDin740ExampleCoupledInertiasKgm2()` = `{2.9673, 6.8673}`
  (exact); `ktrDin740ExampleDrivingSideInertiaCoefficient()` = `0.6983`
  (exact, unrounded); `ktrDin740ExampleShockTorqueNm()` = `2586.4` (exact,
  unrounded `M_A`); `ktrDin740ExampleRequiredMaxTorqueNm()` = `3750.3`
  (exact, unrounded) — all within `ktr-din740-benchmark.test.ts`'s own
  documented tolerances of the source's own single-decimal-rounded printed
  figures, and both checks pass either way.
- Difference and explanation: the ~0.26% gap between the source's own
  printed `T_Kmax` requirement (`3760 Nm`) and this file's exact,
  unrounded computation (`3750.3 Nm`) is the compounded effect of the
  source's own single-decimal rounding of `M_A` (`0.7` vs. the exact
  `0.6983`) carried through `T_AN`'s own rounding to `1029` — not a defect
  in either computation, and documented as such in
  `ktr-din740-benchmark.ts`'s own doc comments.

### What this document's own formula reveals about this module's simplification

This document's own general (non-hydrostatic-drive) shock-torque formula,
`T_Kmax >= T_S*S_Z*S_t + T_N*S_t` with `T_S = T_AS*M_A*S_A`, is **a real
disagreement with KTR's other document**, not a restatement of it: the
"Coupling Selection Based on Operating Factors" document
(`context/modules/coupling/stage-1-spec.md` item 2) instead gives
`T_Kmax >= (T_N+T_S)*S_Z*S_t*S_R`. Neither `S_B` (operating factor) nor `S_R`
(direction factor) appears in this document's own general formula — `S_B`
only appears in a separate, explicitly simplified selection path for two
specific coupling families driving hydrostatic loads, and `S_R` does not
appear in this document at all. Recorded as a genuine, sourced disagreement
between two documents from the same manufacturer, not resolved — `0.1.0`
adopts neither verbatim (`stage-2-contract.md` "Decisions" item 3).

`compareModuleShockCheckToKtrDin740` uses the worked example above to
quantify exactly what this module's own simplification
(`required * serviceFactor`, reusing the steady-check shape) costs relative
to this document's own detailed method, for three choices of
`coupling.service_factor`:

| `coupling.service_factor` choice | Module's required torque | Deviation from KTR's own `3750.3 Nm` | Module safety factor | KTR's own safety factor |
| --- | --- | --- | --- | --- |
| `M_A*S_A*S_Z*S_t` (fully composed, `1.8225`) | `3750.3 Nm` | `~0%` (algebraic identity) | `1.280` | `1.280` |
| `S_A` alone (`1.8`, the catalog shock factor) | `3704.0 Nm` | `-1.2%` (understates) | `1.296` | `1.280` |
| `S_A*S_Z*S_t` (`2.61`, omitting `M_A`) | `5370.8 Nm` | `+43.2%` (overstates) | `0.894` **(fails)** | `1.280` **(passes)** |

The module's simplified shape is not wrong — it is algebraically identical
to this document's own detailed method when the engineer supplies the fully
composed factor. The real, quantified risk is that the mass-distribution
coefficient `M_A` depends on the driving/load inertia split, which varies by
installation and which this project cannot compute internally yet (no
released motor/load inertia parameter — `stage-1-spec.md` item 3, Unit 4.7
territory). Omitting it from `coupling.service_factor` can overstate the
requirement enough to reject a coupling this document's own method accepts
(the `+43.2%` row above), or — less dramatically here, but not guaranteed in
general — understate it if the engineer uses only the tabulated shock factor
(the `-1.2%` row above). This module does not protect against either
outcome; the engineer's own choice of `coupling.service_factor` carries this
risk.

This module's own compute path continues to reuse its own steady-check shape
for both cases (Stage 2's own resolved choice,
`stage-2-contract.md` "Decisions" item 3) — `ktr-din740-benchmark.ts` is a
benchmark, not an alternative implementation offered to callers.

## Tolerances and Deviations

- This module's own compute path does not call
  `resolveRequiredTorqueFromPower`: it consumes `screw.drive_torque`
  (already resolved, per case) directly. The KTR reference example (Example
  3 above) validates that formula only at the kernel level; the two R+W
  reference examples run through the real compute path, taking R+W's own
  printed `T_AN` as the already-resolved drive torque.
- KTR's own two documents disagree on the general shock-torque formula
  shape, not just factor values (see "Independent Method or Tool Comparison"
  above). This module adopts neither verbatim; it reuses its own steady-
  check shape for both cases.
- `coupling.service_factor` is applied identically to both the `normal` and
  `peak` cases, even though every source uses a different named factor for
  each.
- R+W's own safety-coupling-specific shock form (`T_AR >= K*T_max`) is not
  implemented or benchmarked — out of this version's scope, since R+W's own
  document states it is specific to torque-limiting safety couplings, not
  the general coupling types this module targets.

## Unsupported Conditions

- `holding` and `emergency_stop` load cases — only `normal` and `peak` are
  resolved.
- Multi-coupling drivelines — one coupling connecting a ball screw's own
  drive shaft to its upstream driving shaft only.
- Torsional-resonance or periodic-vibration checks (R+W's own `f_e` formula
  is sourced but not implemented — no released motor/load inertia parameter
  exists yet).
- Fit-tolerance (h6/h7-class) verification — bore compatibility is a simple
  range check only.
- Stiffness/life derating as a function of misalignment.
- A true zero-operating-speed case — `resolveSpeedSafetyFactor` throws
  rather than reporting an infinite safety factor.
