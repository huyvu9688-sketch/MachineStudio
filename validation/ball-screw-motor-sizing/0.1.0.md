## Purpose and Supported Applications

Given a ball-screw-driven linear axis's own geometry, mass, friction,
orientation, and one full point-to-point operating cycle (a forward move,
an optional return move, an optional dwell), computes the required motor
specifications a servo motor for that axis must meet: acceleration torque,
maximum momentary torque, effective (RMS) torque over the full cycle,
required torque with an engineer-supplied safety factor, operating speed,
required power, total reflected system inertia, and inertia ratio. It
reports required-spec values and pass/fail checks against
engineer-supplied margins — "the engineer takes the number to the
catalog" — the same scope `support-bearing@0.1.0`'s and `coupling@0.1.0`'s
own required-input, no-built-in-table values already use. It does not
check the ball screw shaft's own mechanical viability (buckling, critical
speed, life, static safety factor — `ball-screw@0.1.0`'s own separate
responsibility), select a gearbox/coupling/drive/brake, or match a motor
catalog (ADR-0011 "Output scope").

## Validity Envelope and Assumptions

- One straight ball screw, one motor, direct-connected or through a single
  fixed gear ratio — no multi-stage transmission.
- One full point-to-point operating cycle: a forward move, an optional
  return move (same line, opposite direction), and an optional dwell —
  narrower than `motion-profile@0.1.0`'s own general bounded-5-move
  sequence, deliberately, to avoid inheriting that module's own
  per-move-index port defect (`context/progress-tracker.md` "Open
  decisions").
- Horizontal, vertical, or inclined orientation (`0 <= theta <= pi/2`).
  Validated end to end at exactly `theta=0` (horizontal) and `theta=pi/2`
  (vertical); no published worked example at an intermediate incline angle
  was available.
- Symmetric accel/decel magnitude within each one-way move; forward and
  return moves may use different magnitudes from each other.
- Self-contained per ADR-0011 "Reuse policy": reproduces, rather than
  imports, physics already released in `axis-load-cases@0.1.0`,
  `ball-screw@0.1.0`, `motion-profile@0.1.0`, and `drive-train@0.1.0`. The
  one genuine import is `lib/engine/mechanics` (Unit 6.1) for moment of
  inertia and `Ta = J*alpha`.
- No distinct guide-resistance term separate from Coulomb friction (a
  deliberate scope narrowing versus `axis-load-cases@0.1.0`'s own fuller
  model) — THK's own vertical example was reproduced by mapping its own
  "guide surface resistance" figure onto this module's existing
  `external_force` input.
- No servo-motor holding-torque formula for a stationary vertical/inclined
  dwell — the dwell phase contributes `0` torque to the RMS/momentary
  aggregates. Quantified consequence: `effective_torque` understates THK's
  own printed vertical-example figure by ~29% when a real holding-torque
  phase is present and non-negligible (see "Tolerances and Deviations").
- No motor catalog matching — `required_motor_rated_torque`,
  `required_motor_peak_torque`, and `required_power` are reported
  required-spec values, not pass/fail checks against a candidate motor.

## Reference Examples (Published Worked Examples)

### Example 1 — Omron Corporation, direct-connected ball-screw axis

- Source: `jp.omron.servo_motor_selection_guide@csm-tg-e-3-1`, "Technical
  Guide for Servo Motor Selection" sample calculation, printed pp. 12-13
- Inputs: `M=5 kg` load, `P=10 mm` lead, `MB=3 kg`/`D=20 mm` ball-screw
  shaft, `mu=0.1`, no gearbox, `V=300 mm/s`, stroke `L=360 mm`, cycle
  accel(0.2s)+constant(1.0s)+decel(0.2s)+dwell(0.2s)
- Published/expected result: `JB=1.5e-4`, `JW=1.63e-4 kg*m^2`,
  `TW=7.8e-3 N*m`, `N=1800 rpm`, `TA=0.165 N*m`, `T1=0.173 N*m`,
  `Trms=0.0828 N*m`
- MachineStudio result: reproduced twice — at the kernel level
  (`math.test.ts` "end-to-end: Omron Corporation's own worked example")
  and through `executeModule` (`package.test.ts` "Omron Corporation's own
  worked example, through executeModule")
- Difference: inertia and load torque within 4-6 decimal places (exact
  algebra); torque figures within ~0.6% (source's own 3-significant-figure
  rounding)
- Tolerance applied and why: as above — accounts for Omron's own printed
  rounding, not slack introduced to pass the test
- Pass / fail against tolerance: **pass**

### Example 2 — THK horizontal, WTF2040-2 ball-screw axis

- Source: `jp.thk.example_ball_screw_selection@technico-mirror-2026-08-10`,
  "High-speed Transfer Equipment (Horizontal Use)" worked example
- Inputs: `m1=60 kg`+`m2=20 kg` (80 kg total), `Ph=40 mm` lead, 20mm shaft
  diameter, no gearbox, `Vmax=1 m/s`, `t1=t3=0.15 s`, motor rotor inertia
  `Jm=1e-3 kg*m^2`; screw mass derived from THK's own printed linear
  inertia density (2.96 kg, cross-checked by hand against a solid steel
  cylinder at 7850 kg/m^3 — exact agreement)
- Published/expected result: `J=3.39e-3 kg*m^2` (screw+load inertia),
  `T1=120 N*mm` (friction torque), `Tk=4730 N*mm` (max momentary),
  `Trms=1305 N*mm`
- MachineStudio result: reproduced through `executeModule`
  (`thk-reference-examples.ts`/`.test.ts`)
- Difference: inertia within 0.5%; torque figures within 1% (consistent
  with THK's own 3-significant-figure rounding of intermediate values,
  e.g. its own rounded angular-acceleration figure — `1050 rad/s^2`
  printed vs. `1047.2 rad/s^2` exact)
- Tolerance applied and why: as above
- Pass / fail against tolerance: **pass**

### Example 3 — THK vertical, BLK1510-5.6 ball-screw axis

- Source: same document as Example 2, "Vertical Conveyance System" worked
  example — the key validation target, since it is the exact scenario
  `drive-train@0.1.0`'s own closed-form approximation overstates by ~21%
- Inputs: `m1=40 kg`+`m2=10 kg` (50 kg total), `Ph=10 mm` lead, 15mm shaft
  diameter, no gearbox, `Vmax=0.3 m/s`, `t1=t3=0.2 s`, motor rotor inertia
  `Jm=5e-5 kg*m^2`, "guide surface resistance" `f=20 N` (mapped onto this
  module's own `external_force` input, identically for both directions);
  screw mass derived the same way as Example 2 (1.109 kg, agrees with a
  solid-steel-cylinder cross-check within 0.7%)
- Published/expected result: `J=1.58e-4 kg*m^2`, `T1=900 N*mm` (upward
  load torque), `T2=830 N*mm` (downward), `Tk1=1100 N*mm` (governing
  momentary), and — over seven printed phases including a nonzero `658
  N*mm` stationary holding torque — `Trms=743 N*mm`
- MachineStudio result: `J`, `T1`/`T2` magnitudes, and `Tk1` reproduced
  through `executeModule` within 1%. `effective_torque` through
  `executeModule` is **not** THK's own `743 N*mm` — it computes
  `~527 N*mm` (~29% understated), because the dwell phase always
  contributes `0` torque rather than THK's own real `658 N*mm` holding
  torque (an already-disclosed scope gap, now quantified). Isolated from
  that gap, `resolveEffectiveTorque` fed THK's own seven printed phases
  directly (including the `658 N*mm` term) reproduces `743 N*mm` within
  0.5% — direct confirmation the N-phase Trms formula itself, the actual
  ADR-0011 structural fix, is correct.
- Tolerance applied and why: 1% on `J`/`T1`/`T2`/`Tk1` (THK's own
  3-significant-figure rounding); 0.5% on the kernel-level `effective_torque`
  reproduction fed THK's own phases directly; no tolerance applies to the
  `executeModule`-path `effective_torque`, since it is explicitly not
  claimed as reproduced there
- Pass / fail against tolerance: **pass** (for every figure actually
  claimed as reproduced; the disclosed `executeModule`-path
  `effective_torque` gap is recorded under "Tolerances and Deviations",
  not silently passed)

## Independent Method or Tool Comparison

**Satisfied (2026-08-12).** `independent-benchmark.test.ts` cross-checks
this module's own N-phase Trms against `drive-train@0.1.0`'s own
structurally different closed-form `resolveEffectiveTorque` (a
single-scalar `rms_acceleration` approximation), both run through their
own module's real `executeModule` path against THK's own two published
worked examples (reusing `drive-train@0.1.0`'s own already-tested THK
fixtures directly).

- Independent method/tool: `drive-train@0.1.0`'s own released, immutable
  `resolveEffectiveTorque` closed form
- Case(s) compared: THK horizontal (Example 2) and THK vertical (Example 3)
  above
- Result from independent method: `drive-train@0.1.0` reproduces THK's own
  horizontal `Trms=1305 N*mm` within 1%, and computes `~901 N*mm` for the
  vertical case (`validation/drive-train/0.1.0.md` "deviations")
- MachineStudio result: this module's own N-phase Trms agrees with
  `drive-train@0.1.0` within 1% on the horizontal case and reproduces
  THK's own printed `743 N*mm` within 0.5% on the vertical case (kernel
  level, Example 3 above)
- Difference and explanation: the two methods agree closely where
  `drive-train@0.1.0`'s own closed-cycle precondition holds (constant load
  torque, no holding phase — the horizontal case) and diverge by ~21%
  where it is violated (asymmetric load torque, nonzero holding phase —
  the vertical case), reproducing, not merely resembling, the exact gap
  `validation/drive-train/0.1.0.md` already discloses. This is the actual
  evidence the structural fix works, not just a plausible-looking number.

## Tolerances and Deviations

- `effective_torque` understates THK's own printed vertical-example figure
  (`743 N*mm`) by ~29% through the real `executeModule` compute path,
  because the dwell phase always contributes `0` torque rather than THK's
  own real `658 N*mm` stationary holding torque. The N-phase Trms formula
  itself is not at fault — fed THK's own seven printed phases directly
  (including the `658 N*mm` term), it reproduces `743 N*mm` within 0.5%.
  Recorded as a real, sourced, quantified deviation from an
  already-documented scope gap, not a defect discovered here for the
  first time.
- A finding recorded, not a deviation requiring a fix: `resolveDriveForce`
  (`math.ts`) flips gravity's own sign between the `forward` and `return`
  directions, producing a negative signed `return_load_torque` on THK's
  own vertical example (`-0.83 N*m`, versus THK's own printed unsigned
  `830 N*mm`). Verified by hand this session that this is the
  mathematically correct transform of a fixed-frame force-balance model
  (the same one `axis-load-cases@0.1.0`'s own `resolveAxisLoadPhase`
  already uses, where gravity is a fixed vector and only
  friction/guide-resistance flip) projected onto a single
  travel-direction-relative scalar — and that `resolveMomentaryTorque`
  (`Math.abs`) and `resolveEffectiveTorque` (squares every term) are
  already sign-agnostic, so the sign difference has zero effect on any
  reported output. Not a bug; no code change was needed.
- A Stage 5 finding, corrected in documentation rather than left as a
  disproven blanket claim: this module's own prior "no port links" claim
  was inaccurate — an exhaustive cross-module-link sweep found
  `axis-load-cases@0.1.0`'s own resolved `total_moving_mass` output is
  genuinely link-compatible with this module's own `total_moving_mass`
  input (same parameter ID). Not a calculation-level dependency (ADR-0011
  "Reuse policy" is unaffected) and nothing wires it today (no workflow
  role exists for this module).

## Unsupported Conditions

- Screw mechanical-strength checks (buckling, critical speed, life, static
  safety factor) — `ball-screw@0.1.0`'s own separate, already-released
  responsibility.
- Motor catalog matching or part selection — no candidate motor's own
  rated/peak torque is an input.
- A servo-motor holding-torque formula for a stationary vertical/inclined
  dwell — quantified above as a real ~29% effective-torque understatement
  on THK's own vertical example.
- A distinct guide-resistance term separate from Coulomb friction — this
  module's own scalar force model is narrower than `axis-load-cases@0.1.0`'s
  own fuller model; a mechanism whose guide resistance cannot be disclosed
  as a single external-force-equivalent figure is not directly supported.
- Intermediate incline angles (`0 < theta < pi/2`) — validated at exactly
  horizontal and vertical only; no published worked example at an
  intermediate angle was available this session.
- No `linear-axis@1` or other guided-workflow role — this module is
  standalone in `0.1.0` (ADR-0011).

## Supported Use Limits (Summary)

One ball-screw axis, one motor, direct-connected or single-fixed-gear-ratio,
one full point-to-point cycle (forward/optional-return/optional-dwell),
horizontal/vertical/inclined orientation (validated at exactly horizontal
and vertical). Two required safety factors (`>= 1`) and one required
maximum inertia ratio, no built-in defaults. Validated against three
published worked examples across two manufacturers (Omron, THK) plus one
independent benchmark (a structurally different closed-form computation,
agreeing/diverging exactly as expected). No holding-torque formula for a
stationary dwell — quantified as a real ~29% effective-torque
understatement on a real vertical example when that phase is
non-negligible. No motor catalog matching. Released and registered as
`ball-screw-motor-sizing@0.1.0` 2026-08-13 — the first module in the Motor
Sizing Tool family (ADR-0011).
