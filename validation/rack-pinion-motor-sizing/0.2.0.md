# Module Validation Record — `rack-pinion-motor-sizing` 0.2.0

Addendum to `validation/rack-pinion-motor-sizing/0.1.0.md`, not a
re-validation of the underlying physics. `0.2.0` changes two things per
`docs/superpowers/specs/2026-08-18-motor-sizing-consistency-pass-design.md`:
gravity is no longer an editable input (hardcoded `9.80665 m/s^2`), and
`inertia_ratio_maximum` now resolves to a founder-directed recommended
default of `10` (`motor_sizing.rack_pinion.
inertia_ratio_recommended_maximum`, registry `1.15.0`) rather than a
required no-default value, with the check's own exceeded-case status
downgraded from `fail` to `warning` to match.

**Unlike the other four consistency-pass modules, change 1 here is not
fully behavior-neutral** — see "A Real, Measured Precision Regression"
below.

## What changed from 0.1.0

1. **Gravity dropped as an input.** `manifest.ts` no longer declares a
   `gravity` port; `math.ts`'s own `resolveDriveForce` uses a hardcoded
   `STANDARD_GRAVITY_M_PER_S2 = 9.80665` constant instead.
2. **`inertia_ratio_maximum` repointed.** The port (same key, same
   compute/UI role) now maps to `motor_sizing.rack_pinion.
   inertia_ratio_recommended_maximum` instead of `motor_sizing.
   rack_pinion.inertia_ratio_maximum`. The new parameter carries a
   founder-directed default of `10` — explicitly **not** a
   manufacturer-sourced figure. The original
   `motor_sizing.rack_pinion.inertia_ratio_maximum` parameter is
   untouched and stays referenced by `0.1.0`'s own manifest.
3. **Check status downgraded.** The `inertia-ratio` check's exceeded-case
   `status` changed from `"fail"` to `"warning"` (`checks.ts`).

## A Real, Measured Precision Regression (Not a Behavior-Neutral Change)

Every other Motor Sizing consistency-pass module's own gravity hardcode is
behavior-neutral, because no existing reference-example fixture ever set
`values.gravity` explicitly — they all relied on the registry's own
`9.80665` default, which the hardcode reproduces exactly. This module is
the one exception found: `0.1.0`'s own `atlanta-benchmark.test.ts`
**explicitly overrode** this module's own `gravity` port to
`ATLANTA_GRAVITY_MPS2 = 9.81` — Atlanta Drive Systems' own printed
convention — specifically so the `executeModule`-path comparison against
Atlanta's two worked numerical examples would be exact, not diluted by a
standard-gravity convention difference neither worked example itself
makes. `0.1.0`'s own tolerance for that comparison was 0.01%.

`0.2.0` removes the `gravity` port entirely, so that override is no
longer possible. The real (small) gap between the SI value this module
now hardcodes (`9.80665`) and Atlanta's own printed convention (`9.81`)
therefore now enters the comparison. Measured directly (not estimated)
by temporarily tightening the test assertion and reading the reported
value, then reverting:

- **Horizontal example** (`travelling operation`, p. C-54): relative
  difference is **~0.0079%**. Gravity's own weight term (`mu*M*g`) is a
  minority contributor to the total tangential force here (friction
  only, ~33% of the total at this scenario's own numbers), so the ~0.03%
  gap in `g` itself is diluted.
- **Vertical example** (`lifting operation`, p. C-55): relative
  difference is **~0.0203%**. Friction vanishes entirely on a pure
  vertical lift (`cos(90deg)=0`), so the weight term is 100% of the
  load-torque force and carries the full gravity-convention gap.

Both values are comfortably under the new tolerance
(`lib/modules/rack-pinion-motor-sizing/0.2.0/atlanta-benchmark.test.ts`,
loosened from 0.01% to 0.03% with disclosed margin) and comfortably small
in absolute engineering terms — this is not a defect, and no formula
changed. It is disclosed here as a real, quantified, honestly-measured
consequence of `0.2.0`'s own gravity hardcode, precisely because this
project's own evidence-disclosure culture (`context/ai-workflow-rules.md`)
requires recording a real regression instead of silently widening a
tolerance with no explanation.

## Regression Evidence for the Recommended-Default Change

Change 2 (the recommended-default repoint) and change 3 (the warning
downgrade) are covered by two updated/new tests in `package.test.ts`: one
confirming the exceeded-case check status is now `"warning"`, not
`"fail"`, and one confirming `inertia_ratio_maximum` resolves to `10`
when unset and stays overridable to any other value. Neither of these
touches gravity or the Atlanta benchmark.

## Disclosed, Non-Sourced Default

The `10` figure in `motor_sizing.rack_pinion.
inertia_ratio_recommended_maximum` is **founder judgment, not a
manufacturer-sourced value** — the same disclosure every other Motor
Sizing consistency-pass module's own `0.2.0`/`0.3.0` addendum record
makes (`drive-train/stage-1-spec.md` item 5's own five-source survey
found 2:1 to 100:1, genuinely disagreeing). `0.1.0`'s own required-
no-default parameter and check behavior are unaffected — `0.2.0` is a
new, separate module version, not an edit to a released one.
