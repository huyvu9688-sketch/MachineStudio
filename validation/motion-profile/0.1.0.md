## Purpose and Supported Applications

Resolves the move timing and kinematic profile of a bounded sequence of up
to five single-axis positioning moves (each optionally followed by its own
dwell) sharing one motion cycle — move time, peak velocity, peak
acceleration/deceleration, cycle time, and a cycle-level time-weighted RMS
acceleration demand value — from declared move distances and
velocity/acceleration limits. It does not size any component, select a
servo/drive, decide machine-level cycle time, or resolve interlocks between
mechanisms (`context/modules/motion-profile/stage-1-spec.md` "Purpose").
Downstream modules (ball screw, guide, coupling, support bearing, servo
drive train) consume this timing and dynamics evidence instead of
re-deriving it.

## Validity Envelope and Assumptions

- One to five single-axis positioning moves (move 1 required; moves 2-5
  optional but must be supplied contiguously starting at move 1), each
  optionally followed by its own dwell, as the whole motion cycle.
- Symmetric trapezoidal or triangular acceleration/deceleration profile
  only — the same acceleration magnitude is used for both the accelerating
  and decelerating phase of every move. Asymmetric accel/decel rates and
  jerk-limited (S-curve) profiles are out of scope for `0.1.0`.
- Every supplied `move_distance > 0`, `max_velocity > 0`,
  `max_acceleration > 0`; every supplied `dwell_time >= 0`.
- No structural compliance, resonance/bandwidth limiting, or encoder/servo
  loop dynamics — this module resolves commanded kinematics, not achieved
  closed-loop response.
- The cycle-level `rms_acceleration` output is elementary time-weighted-RMS
  arithmetic over every phase (each move's accel/cruise/decel, each dwell),
  not a manufacturer-specific formula
  (`context/modules/motion-profile/stage-2-contract.md` "Decisions" item 1).

Full detail: `context/modules/motion-profile/stage-1-spec.md` "Validity
Envelope (Proposed)"; `lib/modules/motion-profile/0.1.0/manifest.ts`
`validityEnvelopeSummary`.

Both sources are cited for reference-example reproduction and independent
benchmarking only, not as the origin of the formulas this module
implements: the underlying trapezoidal/triangular kinematics is standard

module, and no source here implies whole-machine compliance with anything.

## Reference Examples (Published Worked Examples)

Three examples are reproduced, from two independent manufacturers (ABB,
Oriental Motor) across **three independent worked scenarios** — unlike
`ball-screw 0.1.0`'s six examples drawn from only two shared scenarios, none
of these three share underlying numbers with each other.

### Example 1 — ABB walkthrough demo

- Source: ABB AN00115 "Trapezoidal Move Calculations," Rev C (EN), p. 2-3
- Inputs: `SPEED = 8`, `ACCEL = DECEL = 16`, `MOVER = 12` (the source's own
  generic, deliberately unit-agnostic "Mint scale factor" units — assigned
  directly as SI meters/m-per-s/m-per-s² here, since the underlying
  kinematics is unit-system-invariant; see the source's own "Scale Factors"
  section)
- Published/expected result: `Ta = Td = 1/2 sec`, `Ts = 1 sec`,
  `T = 2 seconds`
- MachineStudio result: `accelerationTimeS = 0.5`, `decelerationTimeS =
  0.5`, `constantVelocityTimeS = 1`, `moveTimeS = 2` (`resolveTrapezoidalMove`)
- Difference: none — exact match
- Tolerance applied and why: exact (both inputs and outputs are the
  source's own printed integers/fractions)
- Pass / fail: **pass**

### Example 2 — ABB Exercise Answer

- Source: ABB AN00115, p. 6-7 "Exercise" (a 200mm ball-screw move in 1
  second, assuming an equal accel/cruise/decel time split — the "third
  rule")
- Inputs: the exercise's own derived `SPEED = 250 mm/sec`, `ACCEL = DECEL =
  1250 mm/s/s`, `MOVER = 200 mm` — fed forward through
  `resolveTrapezoidalMove`, not the exercise's own inverse direction (target
  time → derived speed/accel), which this module does not implement
- Published/expected result: `Ta = Td = 200 ms`, `Ts = 600 ms`,
  `T = 1 second`
- MachineStudio result: `accelerationTimeS = 0.2`, `decelerationTimeS =
  0.2`, `constantVelocityTimeS = 0.6`, `moveTimeS = 1`
- Difference: none — exact match
- Tolerance applied and why: exact (fed the exercise's own derived
  SPEED/ACCEL/DECEL values; the exercise's own algebra is self-consistent)
- Pass / fail: **pass**

### Example 3 — Oriental Motor EAS6 catalog example

- Source: Oriental Motor General Catalog 2015/2016, p. H-19
  `<Example operation>`
- Inputs: EAS6, vertical, load mass 15 kg, positioning distance 500 mm,
  operating speed 320 mm/s, acceleration 1.5 m/s² (0.15 G), no starting
  speed stated (`Vs = 0`, this module's own scope; the catalog's
  "Acceleration" graph is explicitly the shared accel/decel rate, also this
  module's own scope)
- Published/expected result: positioning time `1.77 s`
- MachineStudio result: `moveTimeS = 1.7758` (`resolveTrapezoidalMove`)
- Difference: `0.0058 s` (~0.33%)
- Tolerance applied and why: `±0.01 s` — this is a graph-read catalog
  reference value ("Confirming Using the Positioning Distance – Positioning
  Time Graph"), not a full-precision formula result, and its own inputs are
  printed to 2-3 significant figures
- Pass / fail: **pass**

## Independent Method or Tool Comparison

**Oriental Motor general asymmetric/non-zero-starting-speed method
(`lib/modules/motion-profile/0.1.0/oriental-motor-benchmark.ts`).** `math.ts`
implements the narrow symmetric, zero-start-speed trapezoidal/triangular
case (`a1 = a2`, `Vs = 0`). Oriental Motor's own catalog page (H-23) prints
a strictly more general method allowing independent
acceleration/deceleration rates and a non-zero starting/ending speed.
`oriental-motor-benchmark.ts` implements that general method as a genuinely
separate computation (not a wrapper around `math.ts`) and is tested in
`oriental-motor-benchmark.test.ts`:

- Independent method/tool: Oriental Motor's own general trapezoidal method
  (`resolveOrientalMotorPositioningTime`)
- Case(s) compared: the general method reduced to the one case both methods
  can express (`a1 = a2`, `startingVelocityMps = 0`), cross-checked against
  `resolveTrapezoidalMove` across representative trapezoidal and triangular
  inputs
- Result: the two implementations agree to floating-point precision in the
  reduced case, as expected for two implementations of algebraically
  identical formulas (unlike `ball-screw 0.1.0`'s THK-vs-Rockford comparison,
  where the two sources use genuinely different formula shapes and
  calibration constants)
- This satisfies the roadmap's "independent benchmark source or tool
  comparison" item for the single-move kinematics.

**No independent benchmark exists for the cycle-level RMS acceleration
output.** It is elementary time-weighted-RMS arithmetic with no
manufacturer-specific formula to benchmark against
(`context/modules/motion-profile/stage-2-contract.md` "Decisions" item 1);
it is corroborated only by the internal-consistency tests in `./cycle.test.ts`
(a one-move cycle reduces to that move's own values, a pure-triangular
cycle's RMS collapses exactly to the acceleration ceiling, adding dwell time
lowers RMS without changing peak values, repeating an identical move is
RMS-scale-invariant). This is a documented gap, not a silent claim of
corroboration — see "Unsupported Conditions" below.

## Tolerances and Deviations

No deviations from the referenced methods are recorded: `0.1.0`'s single-move
kinematics and RMS aggregation are elementary mechanics/arithmetic, not a
manufacturer-specific convention with competing published values (unlike
`ball-screw 0.1.0`'s buckling-margin and equivalent-load-methodology
deviations). The only tolerance of note is Example 3's `±0.01 s`
graph-reading allowance, documented above.

## Unsupported Conditions

- Asymmetric acceleration/deceleration rates and jerk-limited (S-curve)
  profiles are not implemented — only symmetric trapezoidal/triangular.
- More than five moves per cycle is not implemented; the underlying
  `cycle.ts` kernel supports an arbitrary segment sequence, but this
  package's port cardinality does not expose it (a fixed product decision,
  not evidence-backed — `stage-2-contract.md` "Decisions" item 4).
- The cycle-level RMS acceleration output has no published worked example to
  reproduce and no independent benchmark — see "Independent Method or Tool
  Comparison" above.
- No structural compliance, resonance/bandwidth limiting, or encoder/servo
  loop dynamics.
- No catalog search/ranking, component sizing, or interlock resolution —
  this module resolves commanded kinematics only.

## Supported Use Limits (Summary)

`motion-profile` 0.1.0 resolves move timing, peak kinematics, and a
cycle-level RMS acceleration demand value for up to five sequential
single-axis positioning moves (each optionally followed by a dwell), using
symmetric trapezoidal/triangular kinematics only. Three published reference
examples from two independent manufacturers (ABB, Oriental Motor) across
three independent scenarios are reproduced within stated tolerance, and the
single-move kinematics has an independent-benchmark comparison against
Oriental Motor's more general method. The cycle-level RMS acceleration
output has no published example or independent benchmark — a documented,
honest gap, not a silent assumption of correctness. It does not support
asymmetric accel/decel, jerk-limited S-curve profiles, more than five moves
per cycle, or any component sizing. Released and registered as
`motion-profile@0.1.0` 2026-08-12.
