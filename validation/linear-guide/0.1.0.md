## Purpose and Supported Applications

Given a candidate profile-rail linear guide's own catalog rating data and
the resolved force and moment per load case already produced by
`axis-load-cases` (Unit 4.1), this module checks whether that specific guide
is mechanically viable for the axis: it distributes the applied load across
the guide's four blocks, computes each block's equivalent load, checks
static safety on the governing block, and computes nominal (fatigue) life.
It reports a required-spec / pass-fail-with-margin result for a guide the
engineer has already identified by rail size and block arrangement — it does
not search a catalog and rank candidates
(`context/modules/linear-guide/stage-1-spec.md` "Purpose").

## Validity Envelope and Assumptions

- One fixed arrangement: two parallel rails, two blocks per rail, four
  load-bearing points. One-rail and other multi-rail arrangements are out of
  scope.
- Horizontal or vertical installation only. An inclined axis is rejected by
  the input schema. PMI's overhung, wall-mount, and tilted formula sets
  exist in the source but were not transcribed or verified for this version.
- Ball-type rolling elements only (exponent 3, 50 km basis). A roller-type
  guide is rejected by the input schema rather than silently given the ball
  exponent.
- Only the `normal` and `peak` load cases, matching `axis-load-cases
  0.1.0`'s own scope.
- Equivalent load uses PMI's two-or-more-guideways form `PE = |PR| + |PT|`,
  so no moment rating is consumed and no separate moment term is added.
- The life load factor `fW` and the minimum static safety factor are
  **required inputs with no built-in default** — PMI and IKO publish
  differing guidance ranges for both. `fH` and `fT` default to 1.0, the
  value PMI states for its own guideways at the reference condition.
- Nominal life is reported per load case from that case's own equivalent
  load. No duty-cycle mean load is computed by the package, so a
  varying-load duty cycle is not aggregated into a single life figure. (The
  kernel does implement PMI's mean-load formula, and this record's reference
  examples exercise it; it is simply not wired to a released port — see
  `lib/modules/linear-guide/0.1.0/compute.ts`.)
- **Frame assumption that cannot be validated from the input:** for a
  vertical installation, the engineer's free choice of the `axis.v1` `+Y`
  direction must be the in-plane transverse direction. `axis.v1` leaves that
  choice open for a vertical axis and nothing in a resolved force vector
  reveals which way it was made, so the module reports it as an assumption
  on every calculation rather than checking it.
- No preload-dependent stiffness modeling beyond recording the preload
  grade; no lubrication-regime, seal-wear, or rail-deflection modeling.

## Reference Examples (Published Worked Examples)

PMI's Chapter 9 worked example (printed pages B28-B33), model
`MSA35LA2SSFC + R2520-20/20 P II`, is reproduced **end to end**:
`lib/modules/linear-guide/0.1.0/pmi-chapter-9.ts` and its test file.

Given data: `C = 63.6 kN`, `C0 = 100.6 kN`, `m1 = 700 kg`, `m2 = 450 kg`,
`v = 0.75 m/s`, `a1 = 15 m/s²`, `a3 = 5 m/s²`, `t1/t2/t3 =
0.05/1.9/0.15 s`, stroke `1500 mm`, `l1 = 650 mm`, `l2 = 450 mm`,
`l3 = 135 mm`, `l4 = 60 mm`, `l5 = 175 mm`, `l6 = 400 mm`, `fW = 1.5`.

| Reproduced | Count | Tolerance | Result |
| --- | --- | --- | --- |
| Per-carriage radial working load (9.1.1-9.1.5) | 20 figures | ±0.1 N | pass |
| Per-carriage lateral working load, signs included (9.1.1-9.1.5) | 20 figures | ±0.1 N | pass, with one documented source error (below) |
| Per-carriage equivalent load (9.2) | 20 figures | ±0.1 N | pass |
| Governing static safety factor (9.3) | `fs = 11.7`, plus the governing carriage and phase | ±0.1 N on the load; PMI's own one-decimal print on `fs` | pass |
| Per-carriage mean load (9.4) | 4 figures | ±0.1 N | pass |
| Per-carriage nominal life (9.5) | 4 figures | 0.1% relative (PMI prints 3-4 s.f.) | pass |

±0.1 N is the precision PMI itself prints. The reproduction feeds a force
and moment resolved from PMI's own given data through
`resolveBlockLoadsFromResultant` — the module's **real integration path** —
rather than calling the installation-specific functions that merely restate
PMI's printed formulas. Restating a formula proves nothing; running twenty
printed numbers through the code the module actually executes does.

**This is one example from one source.** The table above counts figures, not
independent scenarios, and this record does not treat five phases of one
worked example as five independent examples. Compare `ball-screw 0.1.0`,
which has two manufacturers across two shared scenarios, and
`axis-load-cases 0.1.0`, which has three genuinely independent THK examples.

### What the reproduction settled that earlier stages could not

- **The carriage-numbering map.** Stage 1 declined to reproduce this example
  because it could not confirm how PMI's `No.1`-`No.4` numbering maps onto
  the generic Section 6 `P1`-`P4` convention. It is now pinned from the
  printed sign patterns — `No.1`-`No.4` are `block3`, `block4`, `block1`,
  `block2` — and any other assignment fails the twenty load assertions.
- **PMI's `l1` and `l2`.** The Stage 1 spec read `l1` as the rail spacing
  and `l2` as the carriage spacing. They are the other way round: `l1` is
  the carriage spacing along the direction of travel. See "Tolerances and
  Deviations".
- **`g = 9.8 m/s²`.** PMI computes with 9.8, not standard gravity.
  Established by arithmetic, not assumed: 9.80665 misses PMI's own section
  9.1.1 figures by about 2.7 N, well outside the ±0.1 N band.

## Independent Method or Tool Comparison

**Satisfied.** `lib/modules/linear-guide/0.1.0/iko-benchmark.ts` implements
IKO's own dynamic/static equivalent-load method as a genuine second
computation — the roadmap's Definition of Done item 9 — and reproduces
IKO's own worked "Example 1" (catalog printed pages 15-16, model
`Linear Way ME 25 C2 R640 H`) end to end.

**The series-specific conversion-factor gap that blocked this is closed.**
The Stage 1 spec's item 7 described IKO's `X`/`Y` dynamic-equivalent-load
factor as coming from "a per-series dynamic-equivalent-load-factor table."
Reading IKO's own catalog Table 4 (page 7) directly corrects that: `X`/`Y`
is a universal two-row table keyed only on which of the (already
`kr`/`ka`-converted) radial or lateral load dominates — the same two rows
for every series. Only `kr`/`ka` (Table 3) and their static counterparts
`kOr`/`kOa` (Table 5) are series/size-specific, and the catalog prints those
tables directly — this project does hold them now, for every series IKO
lists, not just the one Example 1 happens to use.

Example 1 is a genuine, in-scope scenario: a two-rail/four-slide-unit
arrangement (catalog Table 6.4), exactly this module's own `0.1.0`
arrangement. It is reproduced with `kr = ka = kOr = kOa = 1` (the `ME`
series, size 15-30 bucket — Example 1's own arithmetic applies no
conversion at all, confirmed against the printed numbers below).

| Reproduced | Count | Tolerance | Result |
| --- | --- | --- | --- |
| Dynamic equivalent load `P1`-`P4` (page 16) | 4 figures | ±2 N (IKO's own inputs are whole-Newton rounded) | pass |
| Static equivalent load `P01`-`P04` (page 16) | 4 figures | exact (no `X`/`Y` weighting to round) | pass |
| Static safety factor `fs = 6.3`, governing unit 1 | 1 figure | IKO's own one-decimal print | pass |
| Basic rating life, ~4410 km | 1 figure | 0.5% relative (cube exponent amplifies input rounding) | pass |
| Service life, "about 73,500 hours" | 1 figure | 0.5% relative | pass |

IKO's own "Example 2" (`MH 45 C2 R1050 H`) is **not** reproduced: its own
worked calculation cites catalog Table 6.2 ("one track rail and two slide
units") rather than Table 6.4, and its static-equivalent-load calculation
carries an extra `(C0/T0)·|M0|` moment term Example 1's does not — IKO's own
mono-rail case, needing the same added moment term PMI's own mono-rail
variant needs and this module's `0.1.0` scope does not cover (item 7,
"Equivalent load" below). Out of scope for the same sourced reason, not an
oversight.

**The open equivalent-load-methodology question is now resolved, for this
series bucket:**

- **Equivalent-load methodology — resolved, not just documented.** For
  `kr = ka = 1`, IKO's `P = X·Frw + Y·Faw` reduces algebraically to
  `PMI's PE − 0.4·min(|Fr|, |Fa|)` — proved, not curve-fit, since `(X,Y)` is
  always `(1, 0.6)` or `(0.6, 1)` depending on which of `|Fr|`, `|Fa|` is
  larger. IKO's figure is therefore always the lower of the two, strictly
  lower whenever both load components are nonzero. On IKO's own four slide
  units the gap runs from about 5% to about 20% of PMI's figure — a real,
  bounded, now-quantified disagreement, neither form "corrected" toward the
  other. A series with an asymmetric `kr`/`ka` (e.g. `MV`, or `ME`/`MH`'s
  own 35-45 bucket) was not checked and may not reduce this cleanly, since
  the dominance comparison would then run over *converted* loads.
- **Static-safety-factor standard values — still open.** PMI's and IKO's
  tables give different ranges for nominally the same operating conditions.
  Neither is adopted; the minimum stays a required input. Unaffected by the
  benchmark above.

This module's own compute path continues to use PMI's `PE = |PR| + |PT|`
form (Stage 2's own resolved choice, stage-1-spec.md "Stage 2 Entry
Criteria" item 4) — `iko-benchmark.ts` is a benchmark, not an alternative
implementation offered to callers.

## Tolerances and Deviations

### Two real defects this validation found and corrected

Both were in the lateral direction, and both trace to the same root cause:
the Stage 1 spec read PMI's `l1` as the rail spacing and `l2` as the
carriage spacing, when they are reversed.

1. **The yawing moment's lever arm was the rail spacing; it is the carriage
   spacing along travel.** Every PMI lateral formula divides by `2·l1`,
   which under the mistaken reading looked like PMI reacting a yawing moment
   across the rails — physically impossible, and recorded at the time
   (`context/modules/linear-guide/stage-2-contract.md`) as a suspicious open
   question rather than trusted. It was PMI's letters that had been misread,
   not PMI's physics. This changed computed lateral block loads, and
   therefore equivalent load, static safety factor, and life, whenever the
   two spacings differ.
2. **The four lateral block loads were given one shared magnitude; they form
   a signed, zero-sum distribution.** PMI's *general* diagrams (B19, B23,
   B24) print a single unsigned magnitude for all four blocks, which the
   kernel reproduced literally. Chapter 9 prints the same magnitude with
   alternating signs that cancel. Four equal, same-signed lateral forces
   cannot balance a yawing moment, so Chapter 9 is the reading that holds
   up.

The evidence for the `l1`/`l2` correction, in order of strength:

- Chapter 9's lateral loads alternate sign across the **same** block pairs
  its `/(2·l1)` radial term separates, and sum to zero. Only pairs separated
  along the direction of travel can balance a yawing moment.
- Chapter 9 divides the height-induced moments `m1·a1·l6` and `m2·a1·l5` by
  `2·l1`. An axial force at a height is a pitching moment, which only the
  fore/aft carriage pair can react.
- B23 does the same with its own `m·a1·l3/(2·l1)`, where `l3` is a height.

### A printing error in the source

**PMI's section 9.1.3 contradicts itself, and this module follows its
formulas rather than its printed values.** For deceleration to the left it
prints `Pt3la3 = −m1·a3·l4/(2·l1)` beside the value `161.5 N`, and
`Pt4la3 = +m1·a3·l4/(2·l1)` beside `−161.5 N` — formula and value opposite
in sign in both cases.

The other three phases (9.1.2, 9.1.4, 9.1.5) each have formula and value in
agreement, and their sign patterns group carriages `{No.1, No.4}` against
`{No.2, No.3}` in every phase, flipping wholesale between accelerating and
decelerating. Reading 9.1.3 by its formulas fits that pattern exactly;
reading it by its printed values would make it the only phase whose lateral
reactions regroup, which no rigid-body arrangement can do.

Nothing downstream in PMI's own example depends on it: equivalent load takes
`|PT|`, every magnitude there is 161.5 N, and sections 9.2-9.5 come out the
same either way — presumably why the slip survived printing. The test
asserts the disagreement is confined to those two carriages and is a sign
flip only, and separately asserts that every printed equivalent load in
9.2.3 still reproduces.

### Other deviations

- **Gravity constant.** The reference reproduction uses PMI's own
  `g = 9.8 m/s²`. A real calculation fed by `axis-load-cases` uses
  9.80665 and will differ accordingly (~2.7 N on this example's base share).
- **Orientation selects no formula.** PMI publishes separate horizontal and
  vertical formula sets only because its method re-derives gravity from
  mass. This module consumes an already-resolved load, so the distribution
  is identical for both installations. `motion.axis.orientation` is retained
  for scope-checking and reporting.
- **A direct lateral force share (`F/4`)** is accepted that no in-scope PMI
  diagram prints, because none shows a net lateral force. Elementary statics
  rather than source-confirmed; passing zero reproduces any PMI diagram
  exactly.
- **This module's own compute path still uses PMI's `PE = |PR| + |PT|`
  form, not IKO's.** `iko-benchmark.ts` implements IKO's own method as a
  benchmark, not as an alternative this module offers callers — the two are
  now known to disagree by a real, bounded amount (see "Independent Method
  or Tool Comparison" above), and PMI's form remains Stage 2's resolved
  choice.

## Unsupported Conditions

- Roller-type guides — rejected by the input schema, not approximated.
- Inclined axes — rejected by the input schema.
- Overhung, wall-mount, and tilted installations.
- One-rail and other non-four-block arrangements.
- `holding` and `emergency_stop` load cases.
- A varying-load duty cycle aggregated to a single life figure.
- Any guide whose most heavily loaded block carries zero equivalent load —
  `compute` throws rather than reporting an infinite safety factor.

## Boundary and Invalid-Input Coverage

`package.test.ts` covers: missing geometry/rating/factor ports; missing

lever arm against the rail-spacing alternative with the two spacings
deliberately unequal.
